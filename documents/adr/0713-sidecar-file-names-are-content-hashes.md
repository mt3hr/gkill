## Context

「HTML で出力」には2つの形がある。単一 HTML（メディアは `data:` URI で中に入る）と、
HTML ＋ 同名フォルダ（ZIP で受け取る）。後者ではフォルダの中にファイルを置く名前を決める必要がある。

元のファイル名をそのまま使うと、4つ問題が出る。

1. **Windows の MAX_PATH。** 深い階層の元パスをそのまま持ち込むと保存できない
2. **使えない文字と予約名**（`:` `*` `?` `CON` `NUL` など）
3. **ZIP の中の日本語ファイル名の文字化け。** 展開するアプリによって結果が違う
4. **実ファイル名そのものが個人情報になりうる。** 出力は gkill を持っていない相手へ渡すもので、
   利用者はファイルの中身を共有するつもりでも、ファイル名に書いた名前や日付まで渡すつもりとは限らない

## Decision

**ファイル名は内容の SHA-256 の先頭 8 バイト（16 桁の16進）＋元の拡張子にする。**

```
出力/3f2a9c1b8e7d6054.jpg
```

拡張子は小文字の英数字だけを許し、無いものや長すぎるもの、英数字以外を含むものは `.bin` にする。
結果として、フォルダの中の名前は ASCII の英数字と `.` だけになり、上の4つがすべて消える。

**内容ハッシュなので重複排除が自動で効く。** 同じ画像が複数の記録から参照されても1エントリで済む。

**表示名は失われない。** 元のファイル名は `IDFKyou.file_name` として焼き込みの JSON の中にある。
HTML から参照する `src` だけがハッシュ名になる。

ZIP のエントリは名前順に並べる。同じ入力なら同じバイト列になり、出力同士を比べられる。

## Rejected alternatives

- **元のパスをそのまま使う** — 上の4つ。とくに4番目は、利用者が気づかないまま渡ってしまう。
- **元のファイル名を安全な字へ変換して使う** — 変換の規則（どの字を落とすか・衝突したらどうするか）を自分で持つことになり、衝突の処理で結局ハッシュか連番が要る。それなら最初からハッシュでよい。表示名は JSON の中にあるので、フォルダの中が読めなくても困らない。
- **`{原寸のハッシュ}_thumb.jpg` のようにサムネイルを原寸に紐づける** — サムネイルだけを出力するときも原寸を読んでハッシュを取ることになる。内容ハッシュなら、原寸とサムネイルは中身が違うので自然に別の名前になる。
- **連番（`0001.jpg`）にする** — 重複排除が効かない。同じ画像が10件の記録から参照されると10回入る。

## Consequences

- **`/files/` 経由で開いた出力 HTML では、同名フォルダの画像が出ない。** そのとき HTML は opaque origin で動き（ADR-0711）、`<img src="出力/xxx.jpg">` に Cookie が付かないので 403 になる。同名フォルダは「ローカルに保存して開く」か「Web サーバに置く」ための形で、gkill に取り込んで開くなら単一 HTML を使う。
- フォルダの中を直接見ても、どのファイルが何なのかは分からない。分かる必要があるときは HTML を開く。
- メディアを「埋め込まない」と同名フォルダは組み合わせられない（フォルダが空になる）。サーバが 400 で弾く。

## Evidence

実測なし —— Windows のパス長と使用不可文字、ZIP の文字コードの扱い、
出力が gkill を持っていない相手へ渡るものであることからの判断。
