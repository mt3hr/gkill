# ADR-0214: サムネイルは拡張子ではなく中身で作る

## Context

画像のサムネイルは `image.Decode` で読んで縮小し、JPEG にして配信していた。ところが**サムネイルの対象を決める `isImage` は37の拡張子を通すのに、`image.Decode` に登録されているデコーダは jpeg / png / gif / webp の4形式しかない**。`.heic` `.avif` `.bmp` `.ico` `.tif` `.svg` などは「画像」と判定されてサムネイル生成へ入り、そこで必ず `image: unknown format` になる。

失敗しても表には出ない。画像の場合は原本をそのまま配信するフォールバックがあり、`http.ServeFile` が拡張子から `Content-Type` を付けるので、ブラウザ側は壊れた画像アイコンになるだけでエラーは出ない。

そして**サムネイル側には失敗を記録する仕組みが無かった**。互換動画には `.failed` の印があるのに、サムネイルは失敗しても何も残さない。結果として、デコードできないファイルは一括生成のたびに全件やり直され、表示のたびに EXIF パースとデコードをやり直していた。

拡張子が実体と食い違っているファイルも同じところで落ちる。`image.Decode` は中身で形式を決めるので `.png` という名前の JPEG は読めるが、中身が BMP や WAV や ZIP のものは読めない。

さらに動画サムネイルには別の欠陥があった。`ffmpeg` の成功を終了コードだけで判断していたため、**exit 0 のまま1フレームも書かなかったとき**に、直後の `os.Rename` が「指定されたファイルが見つかりません」という、ffmpeg が何もしなかったことを隠したエラーになっていた。

## Decision

`image.Decode` が失敗したら **ffmpeg で1フレーム起こす**。ffmpeg は拡張子ではなく中身で形式を決めるので、デコーダの無い形式も、拡張子が実体と食い違っているファイルも、同じ1本の経路で拾える。ffmpeg は動画サムネイルのために既に必須の外部依存なので、新しい依存は増えない。

ffmpeg へ落とす経路は2段にする。1段目は縮小まで ffmpeg の中で済ませる（プロセス1回で終わる）。**それが失敗したら、縮小フィルタを外して原寸で書き出し、Go 側で縮小し直す。**

SVG だけは ffmpeg でもラスタ化できないので、サムネイルの対象から外して原本を配信させる。ブラウザは `<img>` でそのまま描ける。

生成に失敗したら印（`<キャッシュ名>.failed`）を残し、次回以降は生成を試みずに原本へ落とす。互換動画側の `.failed` と同じ形・同じ条件（`ctx` が切れているときは残さない）にそろえる。

ffmpeg の成功は終了コードではなく**出力ファイルの有無**で判定する。出力が無ければ `-ss` を外して1回だけやり直す。

## Rejected alternatives

- **Go の HEIC / BMP / AVIF デコーダを足す** — 形式ごとにライブラリが要り、`.ico` `.tif` `.tga` `.pcx` などは結局そろわない。`isImage` が通す37拡張子を全部そろえるつもりなら依存が際限なく増える。ffmpeg は1本で全部読むうえ、すでに必須の依存になっている。

- **全部 ffmpeg にする（`image.Decode` をやめる）** — jpeg / png / gif / webp は圧倒的多数で、Go 側で読めばプロセス生成が要らない。50万件規模の一括生成でプロセスを50万回起こす理由が無い。EXIF Orientation の適用も Go 側に既にある。

- **`isImage` からデコードできない拡張子を外す** — サムネイルは出なくなるが、`is_image` が false になるので一覧では `<img>` ではなくただのファイル名リンクになる。ブラウザが表示できる `.heic`（Safari）や `.avif` まで見えなくなり、退行のほうが大きい。`is_image` の意味は「画像として表示してよいか」であって「gkill がデコードできるか」ではない。

- **拡張子を一括で正しいものへ改名して済ませる** — 拡張子の誤りは実在するが、それを直しても `.bmp` や `.heic` はやはりデコードできない。加えて IDF の索引は追加専用なので、改名するなら `TARGET_FILE` の更新を対で行う必要があり、データ側の作業になる。コード側の欠陥はコード側で直す。

- **失敗の印を残さない（現状維持）** — 一括生成のたびに、デコードできないファイルを全件やり直す。手元でも毎回まるごとやり直していた。表示のたびにも EXIF パースとデコードをやり直す。

- **ffmpeg が出力を書かなかったら、そのまま `os.Rename` のエラーを返す（現状維持）** — 「指定されたファイルが見つかりません」というメッセージだけがログに残り、原因が ffmpeg 側にあることが読み取れない。実際、この形のエラーは長らく原因不明のまま残っていた。

## Consequences

- **ffmpeg が無い環境では、これまでどおり `image.Decode` のエラーがそのまま返る。** 挙動は退行しない。ffmpeg 前提の機能は増えたが、必須にはしていない。
- **縮小フィルタを付けられない入力がある。** タイルに分割された HEIF がそれで、ffmpeg は内部で complex filtergraph を組んでタイルを貼り合わせるため、こちらの簡易フィルタ（`-vf`）と併用できない。`Simple and complex filtering cannot be used together` で拒否され、**何も書かないまま exit 0** になる。原寸で書き出してから Go 側で縮小する2段目が要るのはこのため。手元で失敗していたファイルのうち最も多い形がこれだった。
- **`.svg` と、実体が壊れているファイルはどうやっても作れない。** SVG はブラウザがそのまま描くので対象から外し、壊れているものは印に焼いて二度と挑まない。
- 失敗の印は**キャッシュ名にファイルサイズを含む**ので、ファイルを差し替えれば別名になり自動で再試行される。手で消す手段は `clear_cache thumb <利用者ID>`（キャッシュディレクトリごと消える）。
- **`ctx` が切れているときは印を残さない。** HTTP 経由ではブラウザが待ちきれずに接続を切ると ffmpeg も一緒に落ちるので、それを恒久的な失敗として焼くと、実際には作れるサムネイルが二度と作られなくなる。互換動画側と同じ判断。
- `CachedThumbNames` は `.failed` を集合に入れない。入れると一括生成側が「生成済み」と数え違える。印そのものは `GenerateThumbCacheFor` が入口で見て早く戻る。
- **ffmpeg が出力を書かなかったときに非ゼロで終わるかどうかは、ビルドと素材で変わる。** 古い `.MOV` は ffprobe が duration を返すのにその1割の位置で exit 0・出力なしになり、合成した1秒の mp4 は同じ条件で非ゼロになる。終了コードを当てにせず、出力の有無だけで判定すること。
- 一括生成の1周は長くなる。これまで即座に失敗していたぶんを実際に ffmpeg で作るようになるため。印が残るので2周目以降は元に戻る。

## Evidence

手元のリポジトリでサーバ起動直後の一斉生成を1周させ、`GenerateThumbCache` が失敗したファイルの先頭64バイトを読んで実体と突き合わせた。分類は4つで、多い順に:

| 分類 | 割合 | 中身 |
|---|---|---|
| 拡張子は正しいがデコーダが無い | 6割弱 | 多い順に `.heic` / `.bmp` / `.svg` / `.avif` / `.ico` / lossless `.webp` |
| 拡張子が中身と食い違う | 2割強 | 最も多いのは中身が BMP の `.jpg` |
| ffmpeg が空出力のまま exit 0 | 数% | 古い `.MOV` と、動画の名前が付いた静止画 |
| ファイルの実体が壊れている | 1割強 | 全バイトがゼロ・0バイト・途中で切れた JPEG/PNG/GIF |

上の2つは ffmpeg へ落とせばどちらも通る。3つめは出力の有無で判定すれば通る。**4つめだけはどうやっても作れない**ので、印に焼いて二度と挑まないことに意味がある。

同じ ffmpeg で、古い `.MOV` に duration の1割の位置を指定すると exit 0 で出力なしになり、位置指定を外すと同じく exit 0 で JPEG が出た。合成した1秒の mp4 では同じ条件で非ゼロ終了になる。**終了コードは当てにならない。**

分類ごとに実ファイルを1件ずつ取って、この ADR のとおりの手順を通した結果、`.heic` / `.bmp` / 中身が BMP の `.jpg` / `.avif` / `.ico` / `.gif` / `.png` / 途中で切れた JPEG / 古い `.MOV` / `.webm` は**すべて作れるようになった**。作れないまま残るのは `.svg`（対象から外した）と、中身が空・全バイトゼロ・HLS のプレイリスト・`image data not found` の WebP だけで、いずれも素材の側の問題。

拡張子と中身の全数照合では、`.CR2` / `.NEF` を名乗る本物の JPEG が最大の塊だった。これらは `isImage` の対象外なので画像として表示されてすらいない。データ側の問題なのでこの ADR の範囲外。

## 追記（2026-09-22）

静止画の経路の前段に vips（libvips の CLI）が入った（[ADR-0222](0222-thumbnail-prefers-vips-cli-then-native-then-ffmpeg.md)）。
この ADR の「`image.Decode` が失敗したら ffmpeg へ落とす」「2段目は原寸で書き出して Go で縮小」「失敗は印に焼く」は
そのまま生きていて、vips が無い環境と vips が読めなかったファイルの経路になっている。ffmpeg の呼び出しには
`-nostdin` と、静止画では `-threads 1` / `-filter_threads 1` が付く（動画のサムネイルは復号スレッドを絞らない）。
印の中身には、3段とも失敗したときは vips のエラーも包まれる。
