## Context

タスクには定型が多い（仕事・美容院・週報）。従来は1件ずつ手で書くしかなく、週次・月次のまとめ入力ができなかった。

メモ帳（KFTL）には既に `？` で日時を1つ固定する書き方があるが、これは1レコードに1つの日時を与えるだけで、
「毎週金曜に12回」を表現できない。

設計で効いた制約が3つある。

1. **gkill は「Kyou は実体、検索は rep を舐める」で出来ている。** 検索・キャッシュ・列・MCP のすべてが
   「レコードは存在する」前提に乗っている
2. **メモ帳のパーサは TypeScript と Go の2実装で、送信経路も2本ある。**
   Web クライアントは自分でパースして REST を1件ずつ叩き、Wear OS / Android / MCP は
   `/api/submit_kftl_text` でサーバにパースさせる。片方だけ直すと片方が動かない
3. **クライアントは本文が変わるたびに全行を解釈し直す。** `use-kftl-view.ts` の
   `refresh_invalid_lines()` が `get_invalid_line_indexs()`（= 全行の apply）を打鍵のたびに呼ぶ

## Decision

- **実体型。** 送信時に候補日時のぶんだけレコードを実際に書く
- 記法は `？？`（ASCII `??`）の**単独行**で開いて同じ記号で閉じる4行ブロック。
  条件・回数/終了日（必須2行）と、既存時・起点（省略可）
- **展開（複製の生成）は送信時にだけ行う。** 行の解釈のフェーズではブロックが
  spec を埋めるだけにして、複製は Go なら実行ループの直前、TS なら `generate_requests()` の最後で作る
- 繰り返しの単位は**同じ spec を共有しているリクエスト群**。支出ブロックは全支払いが
  共有するので、ブロックまるごとが1グループになる
- 3行目の既定は `no`（既存があればその回を作らない）
- 打刻開始のみ（`ーた`）と打刻終了4種（`ーえ` `ーいえ` `ーたえ` `ーいたえ`）では繰り返しを断る
- 1回の送信で作れるのは1000レコードまで。超えたら切り詰めずに送信ごと断る

## Rejected alternatives

- **ルール型（繰り返し定義を1レコード持ち、表示時に展開する）** — カレンダーアプリの定番だが、
  「まだ存在しない Kyou」を検索結果へ出す必要がある。`FindQuery`・rykv/mi の列・キャッシュ・MCP の
  全部に波及し、gkill の前提（レコードは実体）を壊す。未来をどこまで生成するか、
  ルール変更時に完了済みをどうするか、削除の意味は何か、という問題も丸ごと抱え込む
- **`？` を拡張して `？？` を関連時刻の一種にする** — `？` は前方一致で受理する設計なので、
  `？？` を足すと**判定順序の1行に静かな失敗が全部ぶら下がる**。しかも予定日時欄では
  `？` が任意の接頭辞として剥がされ、剥がした残りのパース失敗が握り潰される。
  先に [ADR-0505](0505-schedule-time-field-rejects-related-time-prefix.md) で `？` を禁止して、
  `？？` は完全一致だけを受ける独立した記法にした
- **展開を `ApplyThisLineToRequestMap`（行の解釈）でやる** — 実装は素直になるが、
  クライアントは**打鍵1回あたり最大1000件を作る**ことになる。`get_invalid_line_indexs` は
  既に「行数の多いタブでメインスレッドを掴む」と分かっている経路で、そこへ千倍の仕事を足せない。
  送信時に回すと副産物として「`？？` をブロックのどこに書いても結果が同じ」も手に入る（行順に依存しない）
- **支出を支払い単位で繰り返す** — 汎用の扱い（`？？` は書かれたレコードに付く）ならこうなるが、
  「スーパーで牛乳とパンを買う」を毎週繰り返したいときに支払いごとへ `？？` を書かせることになる。
  店名・関連時刻と同じ**ブロック共有**にした
- **決定的なIDで冪等にする**（内容から ID を導出し、再送は同じ ID の版として書く） —
  Uguisu の月次セットで使っている手だが、こちらでは1件だけ編集したあとの再送が
  その編集を巻き戻す。検索で突き合わせて「あれば作らない」にした
- **既存判定のためにサーバへ専用エンドポイントを足し、両経路から呼ぶ** — 定義が1本になり
  往復も1回で済むが、クライアントが「自分でパースして自分で書く」という現状の形から外れる。
  型別の同一性の定義を両側に書く代わりに、クライアントは期間で1回引いてヒットごとに
  型別データを読む（N+1）ことを受け入れた
- **基底に `CloneForRepeat` の既定実装を置く** — 置くと新しい型で実装を忘れても通り、
  **日時のずれない複製が黙って書かれる**。基底に置かず、型を足したらコンパイルエラーで気づく形にした
- **存在しない日を最も近い日へ丸める**（第5金の無い月を第4金にする、2月の31日を28日にする） —
  `第4金` や `毎月28` と重複して二重に作られる。丸めずにその月を飛ばす

## Consequences

- **同じテキストを何度送っても増えない。** 3行目の既定が `no` なので、送信が途中で失敗したときの
  後始末が「もう一度同じテキストを送る」で済む（KFTL は DB トランザクションではないので、
  失敗しても書けたぶんは残る）
- **展開後は普通のレコードなので、まとめて直せない。** 12件作ったあとにタイトルを変えたければ12件編集する。
  共通のタグを付けておけば絞り込みはできる
- 予定日時を1つも持たないタスクには使えない（繰り返した日付の入れ先が無い）。行エラーで返す
- Web クライアントは1レコード＝1 HTTP POST を逐次実行し、そのあと全件を引き直す。
  上限の1000件を実際に書くと1000往復＋1000並列 GET になる
- 既存判定はクライアント側で**期間1回＋ヒット件数ぶんの往復**になる（サーバ側は型別リポジトリを
  直接引けるので期間1回で済む）。非対称だが結果は同じ
- i18n キーが 927 → 951 になった
- 行ラベルに出せるのは**書かれた回数**まで。実際に作られる件数は候補の計算にアンカー
  （レコードの日時欄）が要り、ラベル生成では request_map を作らないので手元に無い

## Evidence

- 候補日時の計算は Go と TypeScript で**同じケース表**を通してある
  （語彙8種・存在しない日のスキップ・起点ちょうどの除外・N週おきの基準・上限超過）。
  実装が2つある以上、同値であることを表で固定する以外に守る手が無い
- 打鍵ごとの経路に展開を置けない理由は実測ではなくコードから：
  `use-kftl-view.ts` の `refresh_invalid_lines()` は本文の watch で毎回走り、
  同ファイルには「行数の多いタブでは解析がメインスレッドを掴む」と既に書かれている
