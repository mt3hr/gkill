## Context

ADR は「壊れたときに同じ場所を読み直すことになる範囲」＝サブシステム別に採番している。
当初はその帯を10番刻みで切っていた。73本まで増えた時点で、11帯のうち4帯（検索・DAO・
クライアント・MCP）が満杯になった。

満杯になったときに何が起きたかが、git 履歴にそのまま残っている。

1. `0059`（MCP）で 0050-0059 帯が満杯になる
2. 次のコミット `6adf6f85` で、**中身が MCP の ADR 3本（旧 0063 / 0064 / 0065）が、
   空いていた「開発規約と資料」帯へ置かれた**。アンカーは `src/server/gkill/mcp/write_normalization.go`、
   `src/server/gkill/mcp/write_handlers.go`、`src/server/gkill/api/gkill_server_api/get_kyous_mcp_helpers.go` で、
   `.claude/skills/gkill-mcp/SKILL.md` が MCP の関連 ADR として引いている
3. さらに次のコミット `7252d07b` で、ようやく継続帯「0090-0099 MCP（続）」が新設された

3本は、正規の継続帯ができたあとも「番号は採番後不変」の規約により動かせず、
**別のサブシステムの帯に居座ったまま**になった。同じ経緯で旧 0074（`Sources` が MCP 2巡目の指摘、
アンカーが `get_kyous_mcp_*.go`）も検索帯へ逃げていた。

継続帯そのものも副作用を生んだ。README の帯表には「0070-0079 検索（続。0001-0009 が満杯に
なったため）」「0090-0099 MCP（続）」「0100-0109 DAO（続）」の3行が並び、**1つのサブシステムの
決定を読むのに2つの帯を行き来する**必要が出た。これは採番の目的そのものを損なう。

そして 0030-0039（クライアント）は満杯なのに継続帯が用意されておらず、
次にクライアントの決定を書く人には**置き場が定義上存在しない**状態だった。

いずれも「例外もエラーも出ない」。帯の妥当性を見る検査は1つも無く、
`checkADR()` は番号をファイル名の先頭4文字として切り出すだけだった。

## Decision

ADR の番号帯をサブシステム別の**100番幅**にし、全73本を一度だけ再採番した。
帯からの溢れで別サブシステムの帯に居た7本は、内容に合う帯へ戻した。
`verify_docs` の `checkADRBands` が、帯の重なり・帯外番号・**残り空きが10未満の帯**を落とす。

## Rejected alternatives

- **番号を据え置き、帯の定義を「複数レンジ」に拡張する**（`検索 = 0001-0009, 0070-0079, 1000-1099` のように書く） —
  ファイル改名もリンク書き換えも発生しないので最も安全に見える。だが分断が恒久化する。
  MCP の ADR は 0050-0059 / 0090-0099 / 0060-0069 の**3帯に散ったまま**で、
  「MCP が壊れたときに読み直す範囲」を1箇所で示せない。採番をサブシステム別にしている理由が消える。
- **1000番刻みにする** — 4桁に収まる帯が9本しか取れない。現に8サブシステム＋予約4帯を使っており、
  最初から足りない。5桁へ広げるのは既存の `\d{4}` 前提（`checkADR()` の `f.slice(0, 4)`、
  `adrFiles()` の `/^\d{4}-.+\.md$/`、`numsIn` の `/(\d{4})/g`）を一斉に触ることになる。
- **日付ベースの採番にする**（`20260830-01` 等） — 枯渇は起きないが、番号から
  サブシステムが読めなくなる。「同じ場所を読み直す範囲」で束ねるという採番思想を捨てることになり、
  帯の是正どころか帯そのものが無くなる。
- **サブシステムをやめて通し番号にする** — 同上。加えて、索引を番号順に並べると
  関連する決定がばらばらの位置に散る。
- **帯の枯渇を警告（warn）に留める** — `verify_docs` の警告は FAIL しないので、
  今回とまったく同じ経緯（満杯 → 別の帯へ逃がす → 番号不変で固定）をもう一度なぞる。
  逃がした結果は静かで、逃がした本人にも見えない。
- **満杯（空き0）で落とす** — 遅い。空きが1のときに ADR を1本書くと満杯になり、
  次に書く人が落ちる。落ちた人は「帯を広げる」より「空いている別の帯へ置く」を選びやすい
  （それが実際に起きたこと）。空きが10を切った時点で落として、余裕のあるうちに決めさせる。

## Consequences

- **番号は採番後不変という規約を1回だけ破った。** 旧番号を書いた過去のコミットメッセージ・
  レビュー記録・外部のメモは、`documents/adr/README.md` の「旧→新 対応表」を経由しないと引けない。
  対応表は消さないこと。
- slug は1つも変えていないので、旧番号しか手元に無くても slug で探せば必ず見つかる
  （旧 `0053` の `mcp-composite-cursor-strict-limits` は、新 `0604` でも同じ slug のまま）。
- 予約帯（0900-0999 ビルド・テスト・CI / 1000-1099 運用CLI・配布 / 1100-1199 モバイル /
  1200-1299 ポート）は ADR 0件のまま置いてある。`checkADRBands` は 0件を正常として通す。
- 帯表に件数を書かない。書くと ADR が増えるたびに古びる数字を手で持つことになる。
  件数は `checkADRBands` が実ファイルから数える。
- **再採番をもう一度やる必要は無い。** 帯が窮屈になったら、落ちた時点で帯を広げるか
  新しい帯を切る。100番幅の帯は 0900 以降にいくらでも足せる。

## Evidence

- 再採番前の実測: ADR 73本 / 11帯。満杯だった帯は 0001-0009（9/9）・0010-0019（10/10）・
  0030-0039（10/10）・0050-0059（10/10）の4本。うち 0030-0039 だけ継続帯が未定義だった。
- 帯からの溢れ: 7本（旧 0008 / 0037 / 0063 / 0064 / 0065 / 0074 / 0103）。
  うち 0063 / 0064 / 0065 は上記3コミットの経緯で MCP 帯から溢れたもの。
- 移行の規模: ADR ファイル73本を改名、183ファイル・延べ649箇所の参照を書き換え。
  内訳は `ADR-NNNN` 表記、`documents/adr/` 配下のファイル名を書いたリンク、
  および索引とメタ表のリンクで**ラベル側にだけ残る素の4桁**（角括弧の中に `ADR-` を付けずに
  番号だけ書いてある側。ここは番号でもファイル名でもないので、素直に置換すると取り残される）。
- 再採番後の帯の空き: 最も詰まっている MCP 帯（16本）でも残り84。閾値10には遠い。
- 移行時に見つかった罠: `src/server/gkill/mcp/plugin_tools.go` は生の NUL バイトを1個含むため
  ripgrep がバイナリ判定で丸ごとスキップする。ADR 参照が4箇所あるので、
  この種の一括置換を ripgrep で回すとこのファイルだけ静かに取り残される。
  列挙は `git ls-files`、読み書きは Node の `readFileSync` で行った。
