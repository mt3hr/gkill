# ADR-0052: MCP のページングはカーソルを期間上限へ押し下げ、同一時刻のかたまりを割らない

## Context

30年ぶん（56万件）を取りに行くと**サーバが18GBまで膨れ、1ページ目が1時間53分たっても終わらない**状態だった。

原因はカーソルが検索条件に効いていなかったこと。ページを1枚（最大1000件）返すためだけに**毎回全期間を検索し直していた**ので、ページングがサーバ側の仕事をまったく軽くしていなかった。

## Decision

- カーソルを**クエリの期間上限（`CalendarEndDate`）へ押し下げる**
- **同一 `RelatedTime` のかたまりをページ境界で割らない**（`Limit` を少し超えてでも返しきる）
- `NextCursor` は **RFC3339Nano** で返す
- 解釈できないカーソルは**エラーにする**

## Rejected alternatives

- **カーソルを検索条件に効かせない（改修前）** — ページングが仕事を軽くしない。1ページ返すのに毎回全期間を検索する。

- **厳密に `Limit` を守る** — **同時刻の記録が永久に取れなくなる。** 次ページは「カーソルより厳密に前」から始まるので、かたまりの途中で切ると、返しそこねた同時刻の記録が次ページからも漏れる。一括取り込みの IDF や Fitbit の日次指標のように**同時刻が並ぶデータで現実に起きる**。

- **カーソルを秒に切り捨てる** — 同じ秒の内側を漏らす。RFC3339Nano で返す。

- **解釈できないカーソルを黙って無視して1ページ目を返す（改修前）** — 呼び出し側は**同じページを取り続けてページングが終わらない**。エラーにする。ただし日付のみ（`YYYY-MM-DD`）は受け付ける。

## Consequences

`TotalCount` の意味が「全体の件数」から「**カーソル以降の残り件数**」に変わった。

`Limit` は上限ではなく目安になる（同時刻のかたまりぶん超えうる）。呼び出し側が `Limit` を厳密な上限として扱っていると、返ってきた件数で驚く。

## Evidence

- 改修前: 30年ぶん（56万件）の取得で**ピーク18GB / 1ページ目に1時間53分**
- 同じ改修でプラグイン読み取りバッファの初期確保を32MB→64KBにした（プラグイン6本×2ユーザーで常時384MBを占めていた）
