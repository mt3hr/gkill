# ADR-0213: 互換動画へ変換するのは、原本のまま再生できると言い切れないものだけ

## Context

動画は、ブラウザで再生できる形（H.264 + AAC、高さ720pまで）へ変換したものをキャッシュして配信する。変換するかどうかを決める判定は最初から置かれていたが、**一度も有効になったことがなかった**。判定関数は誕生時（2026-02）から1行目が「常に変換する」で、本体はコメントアウトされたままだった。その後の整理でコメントアウトの残骸だけが削除され、無効化の理由は記録として残らなかった。

結果として、すでにブラウザが再生できる H.264 の mp4 まで全件が再エンコードされていた。互換動画キャッシュはローカルストレージを大きく占有していた。

コメントアウトされていた旧実装は、復活させても使えない。ffprobe の JSON はストリームごとに `codec_name` が `codec_type` より**前**に出るのに、`"codec_type":"video"` を見つけてから*後方*の `codec_name` を探していた。映像を必ず読み飛ばし、音声のコーデックを返す。判定軸も映像コーデック名だけで、コンテナ・画素形式・プロファイル・音声コーデックを見ていなかった。

そしてクライアントには**再生失敗の受け皿が無い**。動画は `/files/...` を素の `<video>` に渡しているだけで `@error` ハンドラが無く、再生できないとエラーも出ずに無音の黒枠になる。

## Decision

ffprobe の出力を `encoding/json` で読み、**原本のまま確実に再生できると言い切れるときだけ**変換を省く。分からないもの・probe に失敗したものはすべて変換する。

解像度は判定に入れない。原本が再生できるなら、高さが720pを超えていてもそのまま配信する。

## Rejected alternatives

- **全件変換のまま据え置く** — 動くし、いちばん安全ではある。だが手元のサンプルでは H.264 だけで3割弱を占め、そのぶんの再エンコードは何も生んでいない。占有しているディスクのうち相当量がそれで、同期のたびにその生成時間も払っていた。

- **旧実装（映像コーデック名だけを見る）を復活させる** — パーサが構造的に壊れているので、そのままでは常に音声のコーデックを見る。仮に直しても、コンテナが非対応（`.mkv` 等、対象拡張子は26種ある）・10bit・4:2:2・音声が AC3/DTS のものが素通りし、**再生できない動画が黙って増える**。

- **クライアントに再生失敗のフォールバックを足し、判定は緩くする** — ZIP内閲覧ダイアログには既に同じ形（`@error` でダウンロード導線）がある。ただし今回はサーバ側だけで完結させる方針を採ったので、その受け皿が無い前提で判定を厳しくする側に倒した。判定表はデータとして持っているので、受け皿を足す判断をしたときに緩めるのは1行で済む。

- **VP9 in MP4 も原本のまま配信する** — Chrome / Firefox は再生できるので、無視できない割合がそのまま浮く。だが Safari / iOS は再生できず、受け皿が無い以上「一部の端末でだけ黒枠」になる。変換する側に倒した。

- **高さ720pを超える原本は互換でも変換する（帯域の上限を維持する）** — 変換を省ける対象が「もともと720p以下のもの」だけに減り、削減効果がほとんど消える。原本の解像度は撮影した端末が選んだもので、その端末で再生できている。帯域より無駄な再エンコードの排除を採った。

- **失敗した変換を毎回やり直す（現状維持）** — 失敗する動画は、アクセスのたびにハードウェアデコードの疎通確認（最大4種×15秒）と全 ffmpeg バリアントとフォールバックを繰り返す。失敗の印を残さないと、一括生成は毎回その費用を払う。

## Consequences

- **判定は一方向の非対称でなければならない。** 「再生できる」と言い切れるとき以外はすべて変換する。緩める方向の変更は、再生できない動画が**エラーも出ずに無音の黒枠**になるという形で表に出る。判定表は `videoNeedsCompat` に集約し、ffprobe を実行せずにテーブル駆動で検証できるよう純粋関数にしてある。
- **probe に失敗したときは原本を返さず、変換を試す。** 従来は「probe失敗時は原本で運用継続（安全）」としていたが、受け皿が無い以上それは安全ではない。変換にも失敗したら原本へ落ちる。
- 変換に失敗したら印（`<キャッシュ名>.failed`）を残し、次回以降は原本へ即フォールバックする。**ただし ctx が切れているときは印を残さない** — HTTP 経由ではブラウザが待ちきれずに接続を切ると ffmpeg も一緒に落ちるので、それを恒久的な失敗として焼くと、実際には変換できる動画が二度と変換されなくなる。印を消す手段は `clear_cache video <利用者ID>`（キャッシュディレクトリごと消える）。
- 「変換しなくてよい」の判定はプロセス内に覚えておく。覚えないと、**原本のまま配信する動画はリクエストのたびに ffprobe を起動する** —— 再生は Range リクエストで何度も同じ経路を通るので、シークのたびにプロセス生成を払うことになる。ディスクへ印を残さないのは、判定のやり直しが ffprobe 1回で済み、起動直後の1リクエストぶんで元が取れるため。そのぶん一括生成は毎回、変換しない動画を probe し直すが、これは並列に走るので短い。
- 原本をそのまま配信するようになったぶん、moov atom が末尾にある動画では最初の再生開始が1往復ぶん遅くなる。Range 対応済みなので再生自体は成立する。
- ハードウェアデコードの疎通確認の結果は、ファイルパスではなく映像コーデックでキャッシュする。パスでキーにすると、一括生成で表が動画の本数ぶん際限なく伸びる。

## Evidence

手元の動画を等間隔に抽出して ffprobe にかけたところ、映像コーデックの分布は多い順に HEVC・H.264・VP9・MPEG-4 で、**H.264 だけで全体の3割弱**を占めていた。音声はほぼすべて AAC、画素形式は yuv420p / yuvj420p のみ。

つまり全件変換のもとでは、そのうち3割弱が「すでにブラウザが再生できるものを、同じくブラウザが再生できる形へ作り直す」ためだけに再エンコードされ、その出力を保存し続けていたことになる。互換動画キャッシュはローカルストレージで最も大きな派生キャッシュになっていた。

判定の側の実測は無い。ffprobe 1回ぶんの費用は再エンコード1本ぶんより桁で小さく、比べる意味が無いため。
