## Context

2026-08-18 に「期間を窓へ刻んで複数回 `get_kyous` を投げる」実装を入れ、**翌日 2026-08-19 に撤去した**。

狙いは2つ ——「最初の行が出るまでの時間」を縮めることと、サーバのピークメモリを下げること。**3つとも外した。**

この ADR は「入れなかった」記録ではなく「**入れて、測って、撤去した**」記録である。同じ提案は直感的に何度でも出るので、実際に試した結果を残す。

## Decision

クライアント側で検索を期間の窓へ刻まない。1つの列の検索は `get_kyous` を**1回**で引く。

列に**部分的な結果を出さない**。フッタの件数は `has_loaded` が立つまで出さない。

## Rejected alternatives

- **期間を窓へ刻んで複数回投げる（実際に入れて撤去した実装）** — 3つの理由で駄目だった。

  1. **総時間が伸びる。** 1リクエストぶんの固定費が窓の数だけ掛かる。とくに `getAllTags`（全repの全タグ走査）は rykv の既定クエリでは `tags` が非nullなので条件が必ず真になり**毎回**走る。repのファンアウトと最新版アドレスのスナップショットも同じ。窓数は既定31日で3、1年で6、下限なしで10
  2. **「検索が終わってもスピナーが回り続ける」ように見える。** 1窓目の結果を列へ入れて表示するのに、スピナーを消すのは全窓が終わったあとだから（実機で報告された症状）
  3. **静かに取りこぼす。** サーバの期間判定は2段階で精度が違う —— SQL は `.Unix()`（秒切り捨て）、`passesPeriodFilter` は `time.Before` / `After`（ナノ秒）。境界を秒でずらすと、境界 `S` に対する `S-0.5秒` のレコードが新しい側では `Before(S)` に弾かれ、古い側では `After(S-1秒)` に弾かれて**どちらの窓にも入らない**（秒未満を保持できるプラグイン・git の記録が対象）

- **境界の精度を揃えて（3）だけ直し、窓分割は残す** — （1）と（2）が残る。しかも（1）は固定費なので、窓を増やすほど悪化する構造。

- **列に部分的な結果を出して体感を改善する** — 件数カレンダー・Dnote・Ryuu・フッタの件数はどれも「**列が全件を持っている**」前提で書かれていて、部分状態ではエラーも出さずに間違える。とくに Ryuu は列の配列をサーバ検索の代わりに使うので、間違った「近くの記録」を返す。

## Consequences

ピークメモリのために分割するなら、**固定費を1回で済ませられるサーバの中**でやること。その判断は実データのプロファイルを取ってから行う。

撤去にともない、削除したモジュールがある。

```
src/client/classes/kyou-search-windows.ts   （2026-08-18 追加、2026-08-19 削除）
```

## Evidence

- 固定費の内訳: `getAllTags` は rykv の既定クエリで必ず走る（`tags` が非null）。repのファンアウトと最新版アドレスのスナップショットも1リクエストごと
- 窓数: 既定31日で3、1年で6、下限なしで10
- 境界の精度差: SQL `.Unix()`（秒切り捨て）と `passesPeriodFilter`（ナノ秒）
- 「スピナーが回り続ける」は実機で利用者から報告された
