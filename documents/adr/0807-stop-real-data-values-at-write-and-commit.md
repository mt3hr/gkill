## Context

公開リポジトリに、利用者の実環境・実記録から得た値が長いあいだ混ざっていた。座標・端末 ID・場所 ID（プラグインの testdata）、
実在のリポジトリ名・rep 名・タグ名、実データの件数・容量・所要時間・割合（コメント・ADR・スキル・README）、歩数、
事故や実測や実利用報告を観測した日付、実データから写したテストの時刻、そしてコミットメッセージの同じ値である。
取り除くには全履歴の書き換えが要り、公開後はフォークと GitHub のキャッシュに旧コミットが残る（v1.1.10 のリリースノート参照）。

既存の機械検査（`checkPersonalInfo`、コミットメッセージのフック、NG 語辞書）は実パス・メールアドレス・辞書の語の 3 種しか見ておらず、
上の値はすべて素通りした。規約にも「実データの中身を書かない」とはあったが抽象的で、書いてよい値と書かない値の線引き表は
コミットの直前にしか読まれない位置にあった。ADR のテンプレートは Evidence に「実測値」を求め、空欄を verify_docs が落とすので、
実環境で測った具体値を書く方向の圧力が構造としてあった。

## Decision

実データ由来に見える値を「形」で検出し、AI が書く瞬間は硬い形（座標・端末 ID・場所 ID・歩数など）だけを止めて精密な数値は警告し、
コミットの瞬間は staged の**追加行**に当てて精密な数値・観測日・切りの悪い時刻も止める。
コード・テスト・ベンチ・サンプル由来の具体値は、同じ行に出所を書けば通す。形では見分けられない実在の名前は NG 語辞書が担当する。

## Rejected alternatives

- **資料・コード中の数値を全部禁止する** — 単位付きの件数だけで追跡ファイルに数千行あり、大半はコード由来の件数（テスト件数・ADR 件数・行数）とベンチの値で正当。検査が常に赤になって誰も見なくなる。
- **検査を全ファイルに当てる（追加行に限らない）** — 既存行の具体値で全コミットが止まる。既存の値を消すかは履歴の書き換えと一緒に判断することで、日々のコミットの検査が担うことではない。ADR の Evidence の既存ベンチ値の誤字を 1 文字直しただけで止まらないよう、削除側と同じ値は「持ち越し」として通す。
- **AI が書く瞬間に精密な数値でも利用者へ確認を出す** — 無人で作業を進めているあいだ、確認待ちで全部止まる。書く瞬間は警告だけにして、確認はコミットメッセージと同じ段階（コミットの直前）に寄せる。
- **verify_docs に `--staged` のような追加行モードを足す** — verify_docs は引数が 1 つでもあるとテスト済みの記録（attestation）を残さない。pre-commit が毎回引数付きで呼ぶと記録の意味が変わるので、形の検査は別プロセスにし、verify_docs は件数字句を出すだけ（`--count-phrases`）にした。
- **形の規則を gkill の中に置き、CI でも回す** — CI には「追加行」の基準が無く全ファイル検査になって既存行で赤くなる。規則を調整するたびに gkill の tree が変わり、リリースゲートの全スイートを回し直すことになる。公開リポジトリへ値が入る経路は、ほぼこの利用者の PC からのコミットだけなので、PC の利用者設定側に置いて git フックから「あれば」呼ぶ。
- **出所の目印に「約」「上限」「最大」「既定」を含める** — 実データの容量を「最大 N MB」、件数を「約 N 万件」と書く形が実際に混入していた。目印にすると素通りする。
- **出所の目印を観測日と実データ文脈の数値にも効かせる** — 同じ段落に「テスト件数」と書くだけで観測日が通ってしまう。観測日・万億の数・実データ文脈の数値は目印では通さず、概数か削除にする。

## Consequences

- 書く日付は変更日だけになる。事故・実測・報告の日付を書かないので、「いつ起きたか」は ADR の `Date` とコミットの日付から辿る。
- ADR の Evidence は、実環境で測った値を概数で書く（十数秒・数百 MB・9 割超）。具体値を書けるのはコード・テスト・サンプルデータ由来とベンチの比率だけで、同じ行に出所を書く。
- 検査の本体はこの PC の利用者設定側にあるので、**CI・GitHub の Web 編集・Dependabot・別の PC からのコミットは形の検査を通らない**。これらの経路で値が入っても、次にこの PC でその行を編集するまで気付かない。
- 形で拾えるのは値の形だけで、実在の名前（リポジトリ・rep・タグ・端末・機種・アカウント）は拾えない。NG 語辞書に語を足さない限り、名前は素通りする（辞書は利用者が管理する）。
- テスト系のパスでは精密な数値は注意に落ちる（テストは具体値を書くのが仕事なので）。テストの固定値を実データから写すと注意にしかならない。
- 誤検知で止まったときの逃げ道 `shape-ok` は、コミット時に一覧が出るだけで止まらない。付けるのは利用者の了承があるときだけという約束は、機械では守れない。

## Evidence

書き換え前の履歴に当てた受け入れ検証（すべて概数。対象は書き換え前後の差分と置換対）:

- 硬い形（E7 座標・場所 ID・端末 ID・作品 ID 形のファイル名・時刻付きの Takeout 名）は、書き換えで消した旧値の行を全部拾った。
- 書き換えで変わった行のうち、形で止まるか注意になるのは 4 割強。残りの大半は実在の名前で、辞書の担当。
- 直近の数百コミットの追加行に当てると、止まるコミットは 1 割程度（件数字句と出所の目印で免除したあと）。止まった値を規則ごとに抜き出して判定すると、精密な数値の規則は半数以上が実データ由来だった。
- コミットメッセージは直近の数百本のうち 1 割弱が止まる。書き換えで中身が変わった旧メッセージは 6 割ほどを形で拾い、残りは名前と単位の無い数。
- 書く瞬間の検査は、何も見つからない経路で 1 回あたり百数十 ms 以内（node の起動と辞書の読み取りだけで、git を呼ばない）。
